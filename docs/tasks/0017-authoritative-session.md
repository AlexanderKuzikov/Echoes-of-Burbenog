# 0017 — Authoritative session на Node: один match, два client context

> Статус: выдана кодовой сессии
> Приоритет: P0
> Фаза: 6 — Local cooperative mode
> Следующая приёмка: `0018`; фаза 6 начата

## Контекст

`0016` закрыл фазу 5: вход, `MENU` без потери матча, слот и полный путь от входа до победы. До сих пор client был единственным владельцем `Simulation`, и это было сознательным решением: solo-first, одна реализация правил, никакой сети.

Фаза 6 — первая задача, которая это решение меняет, и менять его нужно аккуратно. Правило из решений уже зафиксировано: server использует ту же реализацию `Game Core`, две независимые версии правил недопустимы. Отсюда следует всё остальное: сервер владеет часами и состоянием, client становится представлением, а его нынешний путь «я тикаю локальный `Simulation`» должен остаться как режим solo по умолчанию, а не быть вырезан.

Главный риск задачи не в сети, а в раздвоении presentation: если remote-режим получит собственную проекцию snapshot, вторую обработку команд и второе отображение, то через две фазы у нас будет два клиента, которые ведут себя по-разному, и определённость, выстроенная в `0004`–`0016`, перестанет быть свойством проекта.

## Цель

Один матч, один серверный `Simulation`, два браузерных контекста видят одно и то же состояние, и команда, отправленная любым из них, применяется один раз на сервере и приходит обоим.

## Решения штаба (приняты, не переигрывать)

1. **Транспорт — SSE плюс POST, без новых зависимостей.** Node не умеет WebSocket сервер из коробки, а писать протокол руками нельзя. Сервер шлёт snapshots и events одним потоком через Server-Sent Events, команды принимает POST-ом: для модели «тики идут на сервере, команды редки» этого достаточно, и `package.json` остаётся без runtime-зависимостей. Альтернатива `ws` отклонена на этой фазе: одна зависимость против преимущества, которое на двух локальных контекстах не измеряется.
2. **Сервер — единственный владелец `Simulation` в remote-режиме.** Такт на сервере, `step()` вызывается там, snapshots уходят по потоку. Клиент не тикает и не применяет команды к своей копии core.
3. **Одна проекция, два источника.** Меняется источник `snapshot` и место отправки команды, а не код presentation. Локальный `dispatchCommand` и сетевой `POST` сходятся в одной функции, которая дальше ведёт себя одинаково: feedback, `commandLog`, счётчики событий, HUD.
4. **Solo остаётся режимом по умолчанию.** Локальный путь не удаляется, потому что он и есть текущий продукт. Remote включается явно, по адресу комнаты.
5. **Версионированный handshake до первого тика.** `protocolVersion`, `contentVersion`, `mapVersion`, `seed` передаются в ответе на подключение; несовпадение любой из них — понятный отказ, а не молчаливое расхождение правил. Это тот же контракт, что описан в `docs/ARCHITECTURE.md`, и он обязан быть проверяемым тестом.
6. **Команда отклоняется сервером, а не клиентом.** Клиент не решает, достаточно ли золота и свободен ли pad: он отправляет намерение и получает `accept` или `reason` оттуда, кто владеет состоянием. Причина отказа принадлежит серверу, и `replay-in-progress`-подобные клиентские коды сюда не переносятся.
7. **Один core, две роли.** `src/game-core/*` не меняется ни в чём. Сервер создаёт `Simulation` из того же content, что и solo-путь, и никакой второй реализации правил не появляется.

## Входит в задачу

- `src/server/` (новое) — HTTP-сервер на `node:http`, комнаты, такт, snapshot-поток, приём команд, версии в ответе.
- `src/protocol/` (новое) — версионированный контракт: типы и предикаты, общие для сервера и клиента; проверка версий живёт здесь, а не в каждой стороне.
- `src/main.ts` — режим solo/remote, подключение к комнате, единая точка отправки команды, отображение server-owned причин отказа, отключение локального такта в remote.
- `index.html` — вход в комнату и отображение её состояния, по образцу оверлея `0016` без нового визуального языка.
- `tests/smoke.spec.ts` — сценарий с двумя browser context: один матч, одна команда, одно состояние; позднее подключение догоняет состояние; несовпадение версий отказывает.
- `package.json` — скрипт запуска сервера, новых зависимостей нет.
- `docs/ARCHITECTURE.md`, `docs/DECISIONS.md`, `docs/PLAN.md`, `docs/CONTEXT.md`, этот файл, `docs/screenshots/` — контракт, решение о транспорте и evidence.
- `src/game-core/*`, content, `scripts/build-assets.ts`, `src/asset-budgets.ts`, `src/asset-registry.ts` — не меняются.

## Порядок работы

1. Описать протокол в `src/protocol/`: версии, формат команды, формат snapshot и событий, предикаты совместимости. Никаких глителей и никаких «просто передадим объект».
2. Собрать сервер: комната по идентификатору, такт на `setInterval` с фиксированным шагом, `Simulation` из content, snapshot и события по SSE, команды по POST с проверкой роли и причиной отказа.
3. Собрать клиентскую сторону: подключение, handshake, приём потока, отправка команд в одну общую функцию, которая дальше идёт в тот же путь, что и локальная команда.
4. Перевести solo-режим на ту же точку отправки, не ломая его поведение и не удаляя локальный такт.
5. Показать различие на экране: имя комнаты, число подключённых клиентов, режим. Никаких лишних панелей.
6. Написать E2E с двумя контекстами: первый создаёт комнату, второй подключается, команда отправляется из первого, оба видят одинаковые tick, gold и `eventCounts`; затем позднее подключение и отказ по версиям.
7. Обновить документацию: решение о транспорте в `docs/DECISIONS.md` с альтернативой `ws`, схема потоков в архитектуре.

## Acceptance

- `npm run typecheck`, `npm run build` проходят; новых npm-зависимостей нет, `package-lock.json` в diff не входит.
- `npm run test:core` — те же `status victory, tick 323, gold 229`: core не менялся.
- `npm run test:assets` — те же 11 красных проверок, артефакт прежний.
- `npm test` проходит: не меньше 36 сценариев, минимум три полных прогона подряд и нагрузочный `--repeat-each=2`.
- Сценарий с двумя browser context: одна комната, одна команда, оба контекста показывают одинаковые `tick`, `gold`, `pads` и `eventCounts`; расхождение проверяется сравнением, а не просмотром.
- Позднее подключение получает актуальное состояние целиком, а не пустой матч.
- Несовпадение `protocolVersion`, `contentVersion` или `mapVersion` даёт отказ с причиной, и матч не начинается.
- Команда, отклонённая сервером, показывает server-owned причину и не меняет клиентское состояние; клиент не решает исход сам.
- Remote-режим не тикает локально: без стока от сервера tick не растёт.
- Solo-режим не изменился: все существующие сценарии остаются зелёными, локальный такт на месте, `commandLog` и replay работают как раньше.
- Core и content не изменены; правил матча не появилось вторых.
- Красный прогон обязателен: убрать проверку версии в handshake или разрешить клиенту локально применять команду в remote-режиме — соответствующий сценарий обязан стать красным.
- `git status` после `npm test` чистый; `docs/screenshots/` обновлены.

## Не входит

- Permissions, reconnect, late join, kick — `0018`.
- PvP и mode-specific правила — `0019`.
- Handshake безопасности и anti-cheat boundary — `0020` (в текущем roadmap).
- Matchmaking, identity, rooms с именами, persistence сессии на диск, наблюдение за сессией.
- Wails, dedicated Go server, бинарный протокол, WebSocket.
- Интерполяция и предсказание между snapshot'ами: сначала измерение задержки, потом оптимизация.
- Art direction и новые визуальные элементы.

## Проверка

```text
npm run typecheck
npm run build
npm test
npx playwright test --repeat-each=2
```

Сценарий с двумя контекстами обязан использовать два настоящих browser context, а не две вкладки с общим состоянием: общая вкладка не проверит ничего, потому что состояние у неё одна.

- команды и результат, список screenshots;
- остаток проблем и что уходит в `0018`;
