# 0015 — Сохранение матча по command log: один слот в localStorage

> Статус: выдана кодовой сессии
> Приоритет: P0
> Фаза: 5 — Offline singleplayer
> Следующая приёмка: `0016`; фаза 5 начата

## Контекст

`0014` закрыл точность replay: команда применяется на том тике, на котором была записана, независимо от того, сколько тиков прошло за кадр. Это не только починка QA-механизма — это то, на чём теперь держится сохранение.

Полное состояние матча не нужно сохранять. Seed, версия content и tick-упорядоченный command log — это весь вход симуляции, а состояние есть чистая функция этого входа. Значит восстановление сводится к пересимуляции с нуля до сохранённого тика, и thanks `0014` результат совпадает бит-в-бит. Альтернатива — serialize `MatchSnapshot` и restore в core — сознательно отложена (`EOB-010`), потому что это меняет границу core и требует отдельного решения; брать её первой было бы ошибкой порядка.

Продуктовая часть тривиальна и неинтересна сама по себе. Интересна одна вещь: сохранение не должно стать второй машиной состояния. Если рядом с save/restore появится собственный набор правил, client перестанет доверять core, и определённость, которую `0004`–`0014` выстраивали, развалится.

## Цель

Игрок может сохранить матч, перезагрузить страницу и получить тот же матч: тот же тик, то же золото, та же волна, та же поза. Один слот, локально, без сервера.

## Решения штаба (приняты, не переигрывать)

1. **Сохраняется command log, а не snapshot.** Формат: версия схемы, `seed`, версия content, `tick`, и записи `{ tick, command }` в исходном порядке. Всё, что не выводится из этого, — presentation state, и собирается заново.
2. **Восстановление — пересимуляция, а не restore.** Клиент создаёт новый `Simulation` из того же config, проигрывает log на исходных тиках и останавливается на сохранённом тике. Ровно тот путь, что уже есть в replay, — новая механика не изобретается.
3. **Один слот, `localStorage`, ключ с версией.** `echoes-of-burbenog:match:v1`. Несколько слотов, импорт, экспорт и облако — вне scope: это уже `0019` и дальше.
4. **Несовпадение версий — отказ с причиной, а не тихая перезапись.** Формат payload или версия content не совпали: сохранение не загружается, игрок видит причину, слот остаётся нетронутым до явного действия. Поведение — как у asset contract из `0010`, потому что это тот же случай: испорченный входный артефакт.
5. **Никаких игровых правил в client.** Валидация payload — это проверка формы и версий, а не моделирование правил. Всё, что меняет состояние матча, идёт только через `Simulation`. Если проверка требует знания о балансе — она в wrong place.
6. **Явные действия вместо магии.** Save, Load, New match. Никакого автосохранения по таймеру и никакого «восстановить при следующем открытии» без индикации: игрок должен видеть, что слот есть, и решать, что с ним делать.
7. **Терминальное состояние сохраняется как есть.** Побеждённый матч остаётся побеждённым после перезагрузки, а не превращается в новую preparation. Restart и New match — разные действия с разными последствиями, путать их нельзя.

## Входит в задачу

- `index.html` — контролы Save / Load / New match и индикатор наличия слота, по образцу существующих контролов и `data-testid`.
- `src/styles.css` — состояния контролов и индикатора, ничего кроме них.
- `src/main.ts` — сериализация и валидация payload, сохранение, пересимуляция до тика, применение presentation-слоя, отказ по версиям.
- `tests/smoke.spec.ts` — сохранение на известном тике, перезагрузка страницы, полное совпадение состояния; отказ по несовпадению версии; New match очищает слот и начинает заново.
- `docs/ARCHITECTURE.md`, `docs/DECISIONS.md`, `docs/PLAN.md`, `docs/CONTEXT.md`, этот файл, `docs/screenshots/` — контракт и evidence.
- `src/game-core/*`, content, `scripts/*`, `src/asset-budgets.ts`, `src/asset-registry.ts` — не меняются.

## Порядок работы

1. Описать payload и его валидацию в одном месте: версия схемы, seed, версия content, tick, записи команд. Валидатор отказывает на неизвестной версии, на нецелом числе тиков, на команде не из известного набора и на записи вне `[0, tick]`.
2. Save: собрать payload из текущих `commandLog` и `snapshot.tick`, записать в слот, показать подтверждение. Сохранение не меняет состояние матча.
3. Load: прочитать слот, проверить версии, создать новый `Simulation` из того же config, проигнать log на исходных тиках до сохранённого тика, восстановить presentation и HUD из snapshot. Презентация собирается тем же путём, что после Restart, без второй реализации.
4. New match: очистить слот и начать с preparation, не восстанавливая старое состояние.
5. Проверить, что после Load активна та же инфраструктура, что и после Restart: guard `replaying`, `matchReports`, `commandCount`, счётчики событий. Load — это Restart плюс остановка на тике, и код не должен расходиться на две ветки.
6. Обновить документацию: persistence seam в архитектуре, формат payload как контракт, и решение о том, что snapshot restore остаётся `EOB-010`.

## Acceptance

- `npm run typecheck`, `npm run build` проходят.
- `npm run test:core` — те же `status victory, tick 323, gold 229`: core не участвует в сохранении и не меняется.
- `npm run test:assets` — те же 11 красных проверок, артефакт не меняется.
- `npm test` проходит: не меньше 24 сценария.
- Сохранение на известном тике, перезагрузка страницы и Load дают полное совпадение: `snapshot.tick`, `gold`, `pads`, `towers`, enemies, `eventCounts`, `commandCount` и поза модели. Совпадение проверяется сравнением, а не просмотром.
- Побеждённый матч после Load остаётся побеждённым: тот же terminal report, `Restart` и `New match` работают предсказуемо.
- Несовпадение версии схемы или content даёт отказ с читаемой причиной и не затирает слот; это проверяется подменой payload в `localStorage` через `page.addInitScript` или `page.evaluate`, без порчи других состояний.
- `New match` очищает слот: после него индикатор слота пуст, а состояние — новая preparation, а не предыдущий матч.
- После Load активна та же инфраструктура replay: `replayIndex` дошёл до конца log, `matchReports` содержит ожидаемое число терминальных отчётов, guard `replay-in-progress` не ослаблен.
- Проверка payload не моделирует правила: она отказывает по форме и версиям, а всё, что меняет состояние, идёт через `Simulation`.
- Красный прогон обязателен: сохранить payload без `tick` или с записью вне `[0, tick]`, и валидатор обязан отказать.
- Core, content, `scripts/*`, общий модуль бюджетов и реестр моделей в diff не входят; новых зависимостей нет.
- `git status` после `npm test` чистый; `docs/screenshots/` обновлены, если изменилась картинка HUD.

## Не входит

- Несколько слотов, профили, импорт и экспорт, облачная синхронизация.
- Serialize `MatchSnapshot` и restore в core — `EOB-010`, отдельное решение.
- Автосохранение по таймеру, автозагрузка без индикации, «продолжить» на экране меню — `0016`.
- Settings, качество графики, язык, раскладка HUD.
- Accounts, сервер, multiplayer, Wails, transport.
- Изменения баланса, волн, башен и экономики.
