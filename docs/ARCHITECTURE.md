# Echoes of Burbenog — ARCHITECTURE

## Цели

- Сохранить независимые границы gameplay, presentation, content и networking.
- Сохранять solo-first product scope, не закрывая будущие multiplayer seams.
- Сделать разработку проверяемой LLM через deterministic scenarios и browser automation.
- Позволить первому прототипу быть плоским, не блокируя переход к 3D.
- Не вводить распределённые сервисы, ECS, physics или account system без измеримой потребности.

## Целевая схема

```text
Content + Assets
       │
       ▼
Game Core (pure simulation)
       ▲
       │
Session / Server
       ▲
       │ versioned protocol
       │
Three.js Client
       ▲
       │
Wails desktop shell (later)
```

Game Core получает команды, выполняет фиксированный simulation step и формирует snapshots и events. Он не знает о DOM, Three.js, Wails, WebView или WebSocket.

## Модули

### Game Core

Отвечает за:

- сущности и устойчивые IDs;
- движение и navigation;
- targeting, attacks, damage и effects;
- экономику и permissions игроков;
- waves, objectives и win/lose;
- server-owned random и fixed tick.

Текущий simulation contract:

- `dispatch(command)` принимает intent и возвращает accept/reason;
- `step()` и `advance(ticks)` выполняют fixed tick;
- `getSnapshot()` возвращает defensive presentation projection;
- `drainEvents()` отдаёт transient события для animation/audio;
- content проходит fail-fast validation до запуска match;
- wave bounty и repair начисляются только при отсутствии leaks.

Snapshot restore и command-log replay в core сознательно отложены до решения перед session layer. Client-side QA replay мага существует только в presentation-слое и core не меняет.

Не отвечает за:

- модели, textures, lights и animation playback;
- DOM, input devices и camera;
- persistent storage, accounts и matchmaking;
- transport-specific serialization.

### Client

Отвечает за:

- Three.js scene, camera и renderer;
- input и selection;
- DOM UI;
- presentation states и animations;
- interpolation snapshots;
- cosmetic effects, которые не меняют authoritative state.

Текущая solo-обвязка:

- Client держит один локальный `Simulation` и тикает его fixed-step accumulator, который накапливает реальное время в `requestAnimationFrame`; core получает только целые тики.
- `MatchSnapshot` — единственный источник presentation state. Towers и enemies — presentation-объекты, адресуемые по `entityId`; они создаются, обновляются и удаляются вместе с snapshot.
- HUD (phase, phase clock, enemy count, objective, result) — проекция snapshot. DOM не считает значения сам и не дублирует счётчики; `data-phase`, `data-kind`, `data-paused` и `data-replay` зеркалят `snapshot.status` и client clock state как проверяемый contract.
- Preparation clock показывает `Awaiting start`, когда `preparationTicksLeft === 0`: content prep-окно короткое, и замороженный `T-00:00` читался как живой таймер.
- Pause — только control часов клиента: `step()` не вызывается, accumulator сохраняет дробную часть, поэтому resume продолжает с того же тика без fast-forward и drift. Commands при паузе продолжают доходить до core.
- Restart — client-side QA replay: новый `Simulation` из того же `config` плюс tick-упорядоченный `commandLog`, который проигрывается тем же `dispatchCommand` на исходных тиках. Пока replay идёт, player-команды заблокированы. Load — тот же replay, остановленный на тике слота, New match — тот же replay с пустым log; все три проходят через `beginRecordedRun`. Persistence описана ниже.
- **Команда replay владеет своим тиком.** Пока есть неприменённая запись log, stepping-цикл ограничен её тиком: `tickCeiling = pending - snapshot.tick`, поэтому кадр не может прошагать через тик команды, даже когда clamp дельты (0.25 с = пять тиков) разрешил бы ему это. Излишек времени остаётся в accumulator и разбирается следующими кадрами, так что часы replay могут на короткий момент отставать от wall-clock — это осознанный размен: точность симуляции важнее ровности часов, а «догоняющий» replay сдвинул бы команды и разошёл прогоны. Тик для сравнения берётся из `snapshot`, а не из отдельного счётчика: каждая точка, трогающая core (`step`, `dispatchCommand`, `restartMatch`), обновляет проекцию, поэтому на входе в кадр она синхронна core.
- `dispatchPlayerCommand` — единственный путь player-команды и в `commandLog`, и в core, поэтому replay-guard (`replaying`) живёт там же: во время replay команда отклоняется с client-причиной `replay-in-progress`, не пишется в log и не доходит до core. Pad-клик, Start Wave и QA seam `dispatch` не могут разойтись в правилах.
- Каждый terminal-матч пишет один `matchReport` (status, tick, gold, integrity, leaks, `eventCounts`), поэтому повторный прогон сравнивается с исходным напрямую.
- Terminal feedback имеет приоритет над command feedback: после victory/defeat строка статуса описывает результат, а не последнюю команду.
- Events из `drainEvents` — только transient presentation: typed-счётчики, bounded combat log, вспышка и наведение башни, burst-ring убийства, flash core. События не меняют state и не используются как источник значений.
- `prefers-reduced-motion: reduce` отключает transient-эффекты и ambient-анимацию в canvas, сохраняя статичное читаемое состояние из snapshot. Скелетный клип в том же списке и не замедляется, а не играет: action не запускается вовсе, кости стоят в rest-позе первого ключа.
- Command events потребляются в той же task, что и сам command, поэтому feedback и счётчики не отстают от ввода на кадр.
- Позднее источник snapshots заменяется на session, а projection остаётся прежней.
- `window.__ECHOES_DEBUG__` — QA seam для browser E2E: snapshot, rendered-счётчики, позиции, screen-координаты build pads, выбранный tower, feedback, `eventCounts` по типам, `recentEvents`, clock/replay state, `matchReports`, `lastRebuild` (состояние, снятое на тике, где остановилась пересборка по слоту), `motion` (включая число mixer'ов и число играющих клипов), asset status со списком загруженных моделей, `assetBudgets` (бюджеты, измеренные величины, флаги выполненных проверок и текущие нарушения), `towerModels` (источник view, id модели, число mesh-узлов, узел crystal, его базовая Y, scale, emissive и состояние клипа: имя, длительность, фаза, время, playing и поза кости) и dispatch. Это не gameplay API.
- **Часы измеряются там, где они идут.** Измерение в E2E не должно проходить через round-trip между тест-процессом и страницей: пока Playwright возвращает управление, страница успевает прошагать несколько тиков, и тест падает на задержке инструмента, а не на продукте (`EOB-017`). Поэтому seam публикует `clockMarks` и `markClock(label)`, а `setPaused` отмечает часы прямо в обработчике клика: mark несёт `tick`, `waveTick`, page-time `performance.now()`, остаток `accumulator` и состояние `paused`. Длительность между двумя отметками не содержит ни одного round-trip, и границы измерений при этом не меняются.
- **Seam умеет поставить кадр на место.** `forceFrameDelta(seconds)` вооружает дельту кадра: пока она задана, каждый кадр списывает ровно это время вместо своего, и значение проходит тот же clamp 0.25 с, что и реальный кадр, — тест не может выдумать кадр, которого продукт не производит. Так как заданное значение делит тик нацело, решётка тиков прогона есть функция от дельты, а не от того, когда браузер добрался до кадра. Это детерминированный способ создать многотиковый кадр вместо ожидания загрузки машины. `commandPlan` публикует по каждой записи log тик выдачи и тик применения, поэтому «команда пришла не на своём тике» читается по паре чисел на конкретной команде, а не по разным терминальным тикам. Продуктовое состояние `forcedFrameDelta` — всегда `null`; это QA-инструмент, а не игровой режим.

### Server и Session

Отвечает за:

- lifecycle матча;
- command validation и permissions;
- simulation ticks;
- client connections и transport;
- room state и later matchmaking;
- persistence adapters.

Server и dedicated server должны использовать одну реализацию Game Core. Нельзя одновременно поддерживать две независимые версии правил.

С `0017` первая сессия существует. Раскладка:

| Модуль | Что это | Граница |
|--------|---------|---------|
| `src/game-core/` | единственная реализация правил | без DOM, Three.js, транспорта и сетевых типов; не менялся |
| `src/protocol/index.ts` | версионированный контракт: версии, формат кадра, место и его роль, глаголы комнаты, команды, коды отказа и предикаты чтения | без DOM, Three.js и Node API; его импортируют комната, страница и E2E |
| `src/server/room.ts` | комната: один `Simulation`, `setInterval` с шагом `TICK_RATE`, места и их роли, права на два глагола, лог команд, суммы событий, рассылка | не решает ничего о матче; правило о матче — ответ core |
| `src/server/http.ts` | транспорт: handshake, SSE-поток, POST команд, POST глаголов комнаты, возврат имени закрытой комнаты, статус комнат | триггеры и заголовки; ни одного правила о матче |
| `scripts/serve-session.ts` | запуск сервера из CLI | импорт `src/server` никогда сам не слушает порт |
| `src/main.ts` | клиент: режим, место, подключение, единая точка отправки команды, единственная точка отправки глагола | меняются источник snapshot и адрес отправки, presentation — нет |

### Протокол сессии

Граница версионирована, и номера объявлены один раз в `src/protocol/index.ts`: `PROTOCOL_VERSION = 1`, `CONTENT_VERSION = 1`, `MAP_VERSION = 1`. `CONTENT_VERSION` оттуда же берёт валидатор локального слота, поэтому «слот против content» и «клиент против комнаты» — одно и то же число, а не два.

**Handshake идёт до первого тика и является отдельным обменом.** Клиент шлёт `POST /api/rooms/<room>/handshake` с `role`, `protocolVersion`, `contentVersion`, `mapVersion`, `seed` и, если он держит место, `seatToken`; комната отвечает либо `{ accepted: true, roomId, clientId, seatToken, seatRole, tickRate, versions }`, либо кодом 409 и `{ reason, found, versions }`, где `found` называет число, которое пришло. Отдельным обменом, а не флагом в URL, потому что `EventSource` умеет только GET и не отдаёт тело ошибки: клиент, который обязан показать причину, не может прочитать её из потока. Проверка живёт в `checkHandshake` и вызывается ровно из одного места — из комнаты, которая владеет числами; ни одна другая строка в проекте версии не сравнивает.

Коды отказа handshake: `handshake-shape`, `role-not-permitted`, `seat-shape`, `protocol-version-mismatch`, `content-version-mismatch`, `map-version-mismatch`, `seed-mismatch`. Отказ означает, что матч не начинается: поток не открывается, локальный core не шагается, и клиент показывает причину на входе.

**Место и роль — это ответ комнаты, а не заявление клиента.** `role` в handshake — это «я какого я клиента», и сегодня это один `player`; право закрывать комнату из токена не выводится. Место (`seatToken`) — единица личности в v1: строка из 22 hex-символов, которую комната выдаёт при первом handshake и принимает обратно при следующем. Вместе с местом комната отдаёт `seatRole`, и это единственный источник роли в проекте:

| Роль | Кто получает | Что может |
|------|--------------|------------|
| `owner` | место, выданное handshake'ом, открывшим комнату | `placeTower`, `startWave`, `restartRun`, `endRoom` |
| `guest` | любое место после первого | `placeTower`, `startWave` |

Роль живёт на месте, а не на соединении, поэтому предъявленный токен возвращает и роль. Место переживает соединение: обрыв освобождает его (`heldBy = null`), но не уничтожает — иначе каждый reconnect был бы новым гостем, а owner терял бы право на свою комнату при перезагрузке страницы. Правил о матче в комнате по-прежнему нет: `placeTower` и `startWave` уходят в core как есть, любому месту, потому что доска и aether общие; раздельная экономика — `0019`.

Токен места комнате известен или нет. Известный — место возвращается вместе с ролью. Неизвестный — комната выдаёт это место заново под тем же токеном: роль из токена не читается никогда, поэтому угаданный токен не даёт ничего, чего клиент не получил бы и так, придя первым, а отказ был бы тупиком (комната, выдавшая токен, могла быть просто пересоздана). Отказ получается один и настоящий: токен не той формы, что комната читает (`seat-shape`), и клиент, получив такой отказ, перестаёт предъявлять этот токен.

**Занятое место: выигрывает последнее соединение.** Когда токен предъявлен, а место уже держит другое живое соединение, место переходит к новому: комната отправляет прежнему держателю кадр `closed` с `closure.reason = 'seat-taken'` и `found` — именем нового клиента, снимает его с потока и останавливает такт, если других не осталось. Мнимого «выгнать игрока» в v1 нет и быть не может: без accounts гостя не отличить от переподключающегося, поэтому место не дублируется, а передаётся, а проигравший получает имя виновника, а не вердикт без причины.

**Поток — один, формат кадра один.** `GET /api/rooms/<room>/stream?client=<id>` отдаёт `text/event-stream`; каждый кадр — `data: {…}`.

| Поле | Смысл |
|------|-------|
| `kind` | `state` — кадр, открывающий соединение, `tick` — что изменил такт, `closed` — последний кадр соединения |
| `seq` | монотонный номер кадра комнаты; два клиента сравнимы только на общем `seq` |
| `sentAt` | часы комнаты в момент отправки; клиент считает по ним `deliveryMs` |
| `tickRate` | шаг комнаты, чтобы клиент не считал его своим |
| `players` | сколько клиентов в комнате, по счёту комнаты |
| `snapshot` | `MatchSnapshot` как есть, без обёртки и без диффа |
| `eventCounts` | суммы событий с начала матча — их владелец комната, не страница |
| `events` | события именно этого кадра, для presentation |
| `commandCount`, `commands` | длина лога комнаты и сам лог целиком, когда он вырос для этого соединения |
| `versions` | на `state`-кадре: что комната.run |
| `closure` | только на `closed`: `room-closed` или `seat-taken`, кто закрыл и кто занял место |

Каждый кадр проверяется на клиенте через `readSessionFrame` до попадания в проекцию: кадр, который этот build прочитать не может, отказывает весь поток, а не подмешивается в матч. `closure` обязателен на `closed` и запрещён на остальных: уведомление, прочитанное с живого кадра, убрало бы клиента из комнаты, в которой он ещё находится.

**Команды идут POST-ом и получают ответ комнаты.** `POST /api/rooms/<room>/commands` с `{ clientId, command }` возвращает `{ commandId, accepted, reason?, tick, seq }`. Форма команды проверяется `readCommandRequest` — тем же предикатом `isKnownCommand`, которым пользуется валидатор локального слота: артефакт, который клиент принимает, и тело, которое комната принимает, не могут иметь две грамматики. Причина отказа — ответ core, переданный без изменения; коды `pad-occupied`, `not-enough-gold`, `unknown-pad`, `unknown-tower`, `match-finished`, `wave-already-active` плюс серверные `command-shape`, `command-unreadable`, `session-unreachable`, `session-not-live`. Кадр уходит **до** ответа, поэтому клиент, услышавший `accepted`, уже получил следствие.

**Два глагола комнаты идут вторым POST-ом, за одной дверью.** `POST /api/rooms/<room>/lifecycle` с `{ clientId, verb }`, где `verb` — это `restartRun` или `endRoom`, возвращает `{ verb, accepted, reason?, role, tick, seq, players }`. Форму читает `readLifecycleRequest`, ответ — `readLifecycleAnswer`; `role` в ответе — это то, что комната решила, поэтому отказ читается как «ты гость», а не как загадка. Оба глагола принадлежат месту `owner`; отказ гостю — `owner-only-restart` или `owner-only-end-room`, по одному коду на глагол, чтобы отказ называл именно то, что не разрешили. Отказ не меняет ничего: ни тика, ни лога, ни места.

`restartRun` — это не пересборка на клиенте. Комната создаёт новый `Simulation` из того же конфига, обнуляет лог и суммы событий и рассылает `state`-кадр, поэтому оба клиента приходят в одну preparation тика 0 с пустыми pads. Места при этом не трогаются: прогон — это не комната, и owner, перезапустивший прогон, остаётся owner.

`endRoom` закрывает комнату целиком: `closed`-кадр уходит всем присутствующим, такт останавливается, места и лог очищаются. Имя возвращает транспорт — он владеет картой имён и по принятому глаголу удаляет комнату из неё, так что следующий handshake под тем же именем открывает новую комнату и нового owner. Отдельного «выгнать игрока» нет: в тексте сказано прямо, что комната закрыта и никто больше в неё не сядет.

Схема потоков словами: **тик делает комната** — `setInterval` с шагом `TICK_RATE` зовёт `Simulation.step()`, `drainEvents` даёт события, и один кадр уходит всем подключённым; **клиент не тикает** — в remote-режиме условие такта `mode === 'solo' && !paused && !entryOpen` ложно, локальный core не шагается, не диспатчится и не дранится; **клиент применяет** — `applySessionFrame` суммы событий, события и snapshot отдаёт в тот же `applySnapshot`, который кормит сцену и HUD; **команду отправляет страница** — `submitCommand` в solo отдаёт намерение своему core, в комнате делает POST, и дальше оба пути ведут в одну `reportCommandResult`, которая только показывает то, что ей дали; **глагол отправляет страница** — `sendRoomVerb` идёт в `/lifecycle` и кончается в `reportRoomVerb`, которая тоже только показывает.

Измеримые следствия, на которые опираются тесты:

- **Одна проекция, два источника.** `applySnapshot`, `presentEvents`, `adoptEventCounts` и `reportCommandResult` — общие для обоих режимов. Различаются только `dispatchCommand`/`sendRoomCommand` и источник такта. `commandLog` в комнате — проекция лога комнаты: кадр, пришедший с логом, заменяет список целиком, потому что присылает его целиком.
- **Позднее подключение входит в идущий матч.** `state`-кадр несёт snapshot, суммы событий и лог на момент подключения. Клиент, вошедший на тике 41 в матч, где уже две башни и идёт волна, показывает тик 41, две башни, `towerPlaced: 2` и три команды с их тиками — а не preparation тика 0. Поздний вошедший может строить и запускать волну сразу: это текст, а не механика.
- **Право проверяет комната, страница только показывает.** Гость видит `Restart` и `End room` выключенными, и на каждом контроле стоит код причины (`data-reason`) и подсказка текстом комнаты. Тот же отказ комната даёт и тогда, когда запрос приходит в обход интерфейса: прогон спрашивает `/lifecycle` гостевым `clientId` и получает `accepted: false`, `reason: owner-only-restart`, `role: guest`, при этом тик идёт, лог не растёт и золото не меняется.
- **Клиент не решает исход команды.** В remote-режиме `commandLog` пополняется только из кадра, поэтому отклонённая команда не оставляет в client's log ничего: лог клиента и лог комнаты совпадают entry-for-entry. Золото, pads и число башен на отказе не меняются.
- **Оборванный поток останавливает картинку, а не страницу.** Потеря потока переводит сессию в `offline`, открывает вход и оставляет место при клиенте; счётчик `frames` продолжает расти, а `snapshot`, `seq` и суммы событий стоят, пока комната продолжает тикать для остальных.
- **Reconnect — это тот же handshake и целый кадр, и больше ничего.** Разрыв потока в тесте делается через seam `breakStream`, который идёт по пути `EventSource.onerror`; вход предлагает `Continue`, тот отправляет handshake с тем же токеном места, комната отдаёт тот же `seatRole` и полный `state`-кадр. Комната не хранит для вернувшегося историю кадров и не присылает дельту: второй путь состояния — это вторая реализация матча. Пока клиентов нет, комната стоит на своём тике, и вернувшийся приходит ровно туда, где она остановилась, без catch-up по стенным часам.

### Solo и remote: один клиент, два владельца матча

Solo остаётся режимом по умолчанию, и локальный такт не вырезан: без `?room=` в адресе страница по-прежнему владеет `Simulation`, тикает её на своём accumulator и проигрывает command log на Restart. Room включается только адресом — `?room=<name>` — и никак иначе, потому что режим, который включается сам, — это режим, в котором игрок не знает, где находится.

Режим виден на экране в двух местах, и оба рисуются из одного состояния соединения (`paintSession`): полоса `session-strip` в топбаре (`data-mode`, `data-state`, `data-room`, `data-clients` — `Solo` / `Room <name>` / `Not entered` / `N clients · the room's clock · shared aether` / `Update stream lost` / текст отказа) и панель комнаты на входе. Панель входа в комнате — это тот же слой `0016` и тот же язык: строка состояния, поле с именем комнаты и одна кнопка, которая говорит, что нажатие сделает: `Join room` в solo, `Enter room` в комнате без места, `Continue` когда место у этого браузера уже есть (и это же слово после обрыва потока — тогда нажатие и есть reconnect), `Leave room` в подключённой. Строка локального слота в комнате скрыта, `New match` скрыта, и панель `MATCH SAVE` говорит `Room match · not saved here`: локальный слот описывает другой матч, и показывать его под комнатой — ложь. `Continue` из `.entry-actions` в комнате появляется только над живой комнатой, открытой через `MENU`, — это единственный способ вернуться в матч, потому что кнопка панели комнаты уводит из комнаты.

В комнате выключены ровно те контролы дока, которые действуют на локальный core: `Pause` (часов локально нет — останавливать нечего, и «пауза», которая просто замораживает картинку при живом сервере, была бы расхождением), `Save`, `Load`, `New match`. У каждого своя подсказка, потому что выключенная кнопка с чужой подсказкой хуже отсутствующей кнопки. `Start Wave` и палитра остаются включёнными: это команды, а команды ходят в комнату.

`Restart` и `End room` — два глагола комнаты, и в доке они стоят рядом, потому что это одно решение о комнате. `End room` на solo вообще не появляется, а не висит серым. Оба включаются по месту и по состоянию соединения: место `owner` и живая комната — можно, иначе контрол выключен и несёт на себе код причины (`data-reason`) и подсказку текстом комнаты: `Only the room owner restarts the run` либо `Only the room owner closes the room`, а когда комнаты нет — `There is no room to send this command to`. Роль пишется и в `data-seat`, чтобы разницу между двумя окнами можно было назвать, не читая код.

Про aether сказано в двух местах, и оба — на видимой поверхности: полоса сессии в живой комнате читает `N clients · the room's clock · shared aether`, а подсказка входа в комнате объясняет, что aether общий и что строить и запускать волну может любой клиент, а перезапускать и закрывать — owner. Без этой фразы поздний вошедший читает число на экране как свой кошелёк.

Место переживает вход на страницу, потому что слот — единственное, что браузер хранит: `MatchSavePayload` получил необязательное поле `roomToken`, которое пишется вместе с местом, сохраняется при `Save` и обнуляется, когда игрок стирает слот через `New match`. Поле не часть матча: пересборка слота его не читает, и слот без него пересобирается ровно тот же. В комнате слот не читается как матч (панель по-прежнему говорит `Room match · not saved here`, и это правда — матч здесь не хранится), но место из него достаётся, поэтому один артефакт умеет держать и матч в solo, и место в комнате. Слот, который не читается по другой причине, всё равно отдаёт токен: потерять место из-за несовпадения версии content означало бы тихо разжаловать owner'а в гостя.

Seam добавил `session` (режим, состояние, комната, `clientId`, версии, число клиентов, `seq`, число применённых кадров, отказ, последний ответ на команду, `seatToken`, `seatRole`, `closure`, `connect` с числом handshake'ов, числом предъявленных мест и двумя длительностями в часах страницы, последний ответ на глагол, `deliveryMs`), `frameLog` (ограниченный 400 кадрами журнал применённых кадров: `seq`, `tick`, `gold`, `pads`, суммы событий, `players`, `commandCount`, `at`, `deliveryMs`) и три инструмента: `forceHandshake(overrides)` — чтобы версия, которую объявляет клиент, была достижима из теста без правки сборки; `breakStream()` — разрыв потока тем же путём, каким его рвёт сеть; и `frames` — счётчик отрисованных кадров, без которого «тик стоит» и «страница умерла» выглядят снаружи одинаково. Все меняют инструмент, а не правила: `forceHandshake` меняет, что клиент *говорит*, а не то, что комната *принимает*; `breakStream` идёт по ветке обработчика потери соединения, а не подменяет её.

Окно замера в seam выросло с 64 до 400 кадров не из любопытства, а потому, что при 20 кадрах в секунду 64 кадра — это полторы секунды, а p99 по полутора секундам не бывает хвостом. 400 кадров — это четверть минуты тёплого клиента.

### Protocol

Версионированный boundary между client и server:

- `Command` — намерение игрока;
- `Snapshot` — полное или частичное состояние для presentation;
- `Event` — краткоживущий визуальный факт;
- handshake с protocol version, content version, map version и seed.

Формат сериализации выбирается после измерения размера и частоты snapshots. На раннем этапе приоритет — читаемость и диагностика.

С `0017` контракт описан: он живёт в `src/protocol/index.ts` и разобран выше в разделе «Протокол сессии». Измеренный кадр — 605–685 байт при 15 врагах на экране, 20 кадров в секунду, около 13 КБ/с на клиента; лог команд едет только в кадре, где он вырос. Диффы, бинарный протокол и сжатие — не выбраны и не измерены; смена формата затронет `readSessionFrame` и генератор кадра, и больше ничего.

### Задержка кадра: измерено, порогов нет

С `0017` в приёмке было сказано, что стратегию интерполяции нельзя выбирать по максимуму, вызванному подъёмом второго браузера. `0018` сняла это измерением на прогретом клиенте: окно открывается после того, как оба контекста поднялись и комната пошла, и подъём второго context в окно не входит — иначе измерялась бы стоимость запуска браузера, а не комнаты. Задержка (`deliveryMs`) снимается внутри страницы как `Date.now() - frame.sentAt`, то есть ни одно число не содержит round-trip между процессом теста и браузером; перцентили считаются уже в тесте.

Измерено на этой машине, 10 с окна, 20 тиков/с комнаты, два настоящих browser context:

| Клиент | кадров | p50 | p95 | p99 | max |
|--------|--------|-----|-----|-----|-----|
| a | 148–175 | 1–5 мс | 8–19 мс | 14–63 мс | 15–94 мс |
| b | столько же | 1–5 мс | 7–17 мс | 16–52 мс | 18–94 мс |

Reconnect на прогретом клиенте: handshake 8–11 мс, первый кадр целиком через 14–26 мс от отправки handshake, доставка этого кадра 3–10 мс. Обе величины сняты в странице.

**Порогов не введено и вводить нельзя до `EOB-002`:** предел задержки — это performance budget на эталонной машине, а эталонной машины нет. Числа выше — база для решения об интерполяции, а не приговор ей. Один вывод, который из них следует уже сейчас: хвост в десятки миллисекунд на прогретом клиенте — это шум планировщика и GC, а не сеть, и никакая интерполяция его не лечит.

### Content и Assets

Content включает data-driven описания карт, башен, врагов, волн и баланса. Assets включают GLB-модели, textures, materials и animation clips.

Модели производятся собственным генератором `scripts/build-assets.ts` и не коммитятся: `public/models/` под `.gitignore`, сборка идёт через `predev`/`prebuild`, а `npm test` содержит шаг `test:assets`, поэтому Playwright физически не может увидеть устаревшие артефакты.

Asset contract, как реализовано в `0009`:

- glTF 2.0, Y-up, right-handed, +Z forward, 1 unit = 1 world unit, pivot в центре основания: модель ставится на pad без дополнительных смещений;
- узлы — прямые потомки корня сцены с именами `base`, `stem`, `roof`, `crystal`, `aura`; обязательный узел `crystal` несёт эмиссию и idle bob, остальные имена делают дифф модели читаемым;
- габарит сопоставим с процедурной башней: высота около 1.6, footprint в пределах pad hit radius 0.85, чтобы подмена модели не меняла читаемость сцены и picking;
- один материал на узел: `baseColorFactor` + `metallicFactor` + `roughnessFactor`, `emissiveFactor` у emissive-узла, без текстур; факторы линейные, sRGB-цвета кода конвертирует генератор;
- запрещены сжатие, внешние URI, `extensions` и morph targets;
- скелет и анимация разрешены в узкой форме: один `skin`, один `SkinnedMesh` (узел `crystal`), кости — узлы без mesh, один `AnimationClip` длиной до 2 секунд, каналы только `translation`, `rotation` и `scale` весом `LINEAR`; клик — `crystal-sway` в иерархии `crystal-root > crystal-sway`, поэтому кости достигаются из корня сцены, а `SkeletonUtils.clone` получает их вместе с копией;
- веса кожи считает генератор из своих же массивов: каждая вершина `crystal` привязана к `crystal-sway` с весом 1, `JOINTS_0`/`WEIGHTS_0` — VEC4, то есть 4 слота и 4 влияния против бюджета 4;
- `manifest.json` — единственный источник ожиданий: `id`, `file`, `bytes`, `contentHash`, `triangles`, `emissiveNode`; `file` — имя файла без пути. Скелет в манифест не входит и не должен: клиент меряет его по загруженному дереву, и декларация была бы числом, которому никто не может соответствовать.

Performance budgets и отклонение несовместимого ассета — задача `0010`: лимиты живут в одном модуле `src/asset-budgets.ts`, который проверяется и в сборке, и на клиенте, а числа предварительные до фиксации минимального тестового железа (`EOB-002`).

Все лимиты, их значения и тексты причин отказа живут в одном модуле `src/asset-budgets.ts` — чистые данные и предикаты без Three.js, DOM и Node API, потому что его импортируют и генератор (`scripts/build-assets.ts`), и браузерный клиент. Одна правка лимита обязана ломать и `build:assets`, и рантайм-проверку, поэтому ни в генераторе, ни в `main.ts` нет ни одного числового лимита: только импорт. **Числа предварительные** — заданы штабом под класс встроенной графики (GT 1030 / UHD 620, WebGL2, 8 GB RAM) и пересматриваются после выбора минимального тестового железа (`EOB-002`); до этого решения бюджет ловит грубые нарушения и не ловит плавную деградацию.

Бюджет на модель: 5 000 треугольников, 1 MiB несжатых байт, 32 узла, 32 меша, 16 материалов, 0 текстур, 1 скин, 0 морфов, 1 animation clip, 24 кости, 4 слота веса и 4 влияющих кости на вершину, длина клипа 2 секунды, высота 4.0 world units, footprint-радиус 0.85, pivot по Y — 0 с допуском 0.01. Бюджет на реестр: 8 MiB, 150 000 треугольников, не более 64 моделей. Бюджет сцены в рантайме: 400 draw calls, 250 000 отрисованных треугольников, 32 shader-программы, 1 500 мс на суммарную загрузку ассетов.

Проверка двухуровневая, и обе точки обязаны ловить одно и то же:

- **В сборке.** Генератор измеряет модель (те же округлённые массивы, что попадают в accessors) и прогоняет `checkModelContract`, `checkNodeTypes`, `checkClipTargets` и `checkRegistryBudgets` до первого `writeFileSync`. Нарушение — отказ с ненулевым кодом выхода и внятной причиной; ни артефакт, ни запись в манифест не пишутся, поэтому битая модель не может оказаться рядом со здоровой. Скелет проверяется как структура, а не как число: `verifySkeleton` требует ровно один `skin`, ровно один skinned-узел, длину `inverseBindMatrices` по числу костей, веса в `[0, 1]` с суммой 1 на вершину, `JOINTS_0`/`WEIGHTS_0` типа VEC4 и клип, который адресует только кости и только воспроизводимые каналы.
- **В рантайме.** Клиент сверяет фактическую длину буфера с `entry.bytes` всегда, а `contentHash` — при наличии `crypto.subtle`; расхождение — `AssetContractError` с названием модели и ожидаемым/полученным значением. Дерево загруженной модели проверяется до инстанцирования: любой узел, который client не воспроизводит, — отказ с названием типа узла и путём до него, и то же дерево меряется на скелет. `loadModel` — единственное место, где модель принимается.

Границы различаются по тому, кто может их измерить, и это осознанная граница охвата, а не пробел. Счётчики, которых нет в дереве сцены и которые манифест объявляет — `triangles` и `bytes`, — клиент сверяет с артефактом: `bytes` измеряется, `triangles` берётся из манифеста, и подменой ответа такой отказ воспроизводится. Скелет, наоборот, выводится из того, что загрузилось: число костей — это `Bone` в дереве, слоты и влияния — `skinWeight` геометрии, клипы и длина — `gltf.animations`, а каналы читаются как `gltf`-пути через `gltfPathForTrack` (Three.js называет трек свойством, которое пишет миксер: `crystal-sway.quaternion` — это `rotation`). Поэтому манифест про скелет молчит, а seam публикует измеренное: иначе подмена манифеста не могла бы доказать отказ по костям, а декларация, которой никто не сверяет, выглядела бы как проверка. Геометрические границы — высота, `footprintRadius` и `pivotY` — клиент по-прежнему не меряет: они не выводятся ни из манифеста, ни из дерева сцены, поэтому подменой ответа такой отказ не воспроизвести, а писать непроверяемый клиентский код значило бы создать видимость защиты. Их проверяет генератор на сборке, а в рантайме за ту же границу отвечает picking: клик по pad'у опирается на pad hit radius из content, и бюджет `footprintRadius` существует ровно затем, чтобы модель не могла вылезти за радиус, по которому её выбирают.

`bytes` проверяется всегда, `contentHash` — только при доступном `crypto.subtle`, потому что он требует secure context: localhost и https его дают, голый http по LAN — нет. Молча пропустить проверку нельзя, и сломать легальный dev-сетап тоже нельзя, поэтому seam публикует, какие проверки фактически выполнены, а `scene-status` говорит это текстом: `integrity checked` или `content hash not checked (<причина>)`.

Отказ локальный: одна битая модель не роняет остальной реестр — остальные модели всё равно подменяют placeholder'ы, а отказ называет конкретную модель. Нарушение бюджета сцены не мешает рендерить (сцена уже на экране), поэтому оно публикуется в seam и в диагностике под dev-флагом, но не в строке статуса: бюджет считается на машине, где сцена собрана, и на медленной сети игрок увидел бы «over budget» там, где всё работает.

Причина отказа показывается в трёх формах, и это три разных адресата. Полная — в `assets.error` и в `assetBudgets.failures`, потому что сверять digest нужно с полным значением. В отдельном блоке отказа (`scene-report`, атрибут `data-reason`) та же причина целиком: она переносится по словам и никогда не обрезается, потому что блок для того и существует — одной строке chip'а нечего растягивать, а оператору нужно само значение. В `scene-status` причина сокращена до `sha256:<8 hex>…`, всё остальное без изменений: строка остаётся строкой и говорит, что именно случилось, одной фразой. Сокращение — правило отображения на стороне DOM, а не усечение самой причины, поэтому seam, атрибут и тест остаются точными.

### Две поверхности viewport chrome

Задача `0013` развела то, что видно игроку, и то, что нужно разработчику. Правило простое: **значение, посчитанное на этой машине, не показывается человеку, играющему на своей.**

| Поверхность | Что несёт | Когда появляется |
|------------|-----------|-----------------|
| `scene-status` (одна строка) | состояние загрузки, состав моделей, целостность артефакта, при отказе — короткая причина | всегда |
| `scene-report` (блок) | полная причина отказа с полным digest, в переносе по словам | при `data-assets="error"` |
| `scene-diagnostics` (блок) | бюджеты, измеренные значения, флаги выполненных и пропущенных проверок | только при `?dev` в query |
| seam `assetBudgets` | то же, что диагностика, плюс счётчики `renderer.info` и время загрузки | всегда, в `window.__ECHOES_DEBUG__` |

Флаг диагностики — query-параметр `dev` (`?dev`, `?dev=1`; `?dev=0` и `?dev=false` выключают), а не элемент управления в HUD: панель, свотч и дебаг-оверлей в этой игре не появляются. Элемент `scene-diagnostics` **создаётся** `main.ts` только когда флаг есть, поэтому без флага его нет в DOM вообще — не скрыт и не пуст, а отсутствует, и скриншот без флага не может его показать. `viewport[data-diagnostics]` говорит, какое из двух состояний сейчас. Диагностика перерисовывается вслед за измерением, а не за вердиктом, иначе блок мог бы показывать более старое чтение, чем seam, и сравнивать два момента; игровая строка переписывается только когда меняется причина.

Читаемость проверяется измерением, а не просмотром (`0010`, `0011`, `0013`): «подпись сектора не перекрыта» — это «ни один прямоугольник видимого блока chrome не накрывает ни одного глифа подписи», где подпись меряется через `Range.getClientRects()` по текстовым узлам (сравнение bounding box строк с боксом грид-элемента даёт ложное перекрытие), а «причина видна целиком» — это «каждый глиф причины лежит внутри padding box её блока, блок не обрезан, `text-overflow` не `ellipsis` и `overflow` не scroll». Это одновременно проверка и красного прогона: вернуть `over budget` в строку или обрезать digest в блоке — соответствующая проверка становится красной.

`scene-report` и `scene-diagnostics` — `pointer-events: none`, как остальной chrome: HUD не должен перехватывать клик по pad'у, и в негативных сценариях игрок по-прежнему ставит башню на плитку под блоком.

Favicon объявлен inline data-URL в `index.html` (`EOB-011`): без объявленной иконки браузер сам запрашивает `/favicon.ico`, а отсутствующий файл печатает в консоль `404` на каждом запуске. Проверяется это не запросом (в headless запрос favicon не виден вовсе), а тишиной загрузки: `404` приходит в консоль без URL в тексте, поэтому красным становится проверка «в консоли нет ни одного сообщения уровня error» плюс требование, что объявленная иконка — data-URL.

`renderer.info` и время загрузки — единственные недетерминированные величины: `renderer.info` читается сразу после `render()` (он сбрасывается каждый кадр), а сценовый бюджет пересчитывается только когда хотя бы одно число сдвинулось. Поэтому тест проверяет попадание в бюджет, а не значение.

### Match persistence: один слот, вход матча, а не snapshot

Задача `0015` добавила локальный слот матча. Ключевое решение: **слот хранит вход симуляции, а не её состояние.**

| Поле | Тип | Смысл |
|------|-----|-------|
| `schemaVersion` | `1` | формат самого слота; ключ `echoes-of-burbenog:match:v1` несёт ту же версию |
| `contentVersion` | `1` | версия content, под которую записан слот |
| `seed` | `1337` | seed матча |
| `tick` | целое ≥ 0 | тик, на котором остановлено сохранение |
| `log` | `[{ tick, command }]` | tick-упорядоченный command log в исходном порядке |

`MatchSnapshot` в слоте нет, и это не компромисс, а следствие чистоты core: состояние есть функция от `(config, seed, log, tick)`, поэтому сохранять его — значит хранить вторую копию того, что core уже умеет воспроизвести. Всё, что из входа не выводится (поза клипа, transient-эффекты, фаза башни, выбранный tower), — presentation state и собирается заново.

Восстановление — **пересимуляция на пути replay, а не restore**. `beginRecordedRun(stopTick)` — единственная точка, которая пересобирает матч: новый `Simulation` из того же `config`, `commandLog` заново проигрывается тем же `dispatchCommand` на исходных тиках, presentation собирается из snapshot как после Restart. Restart — это `beginRecordedRun(null)`, Load — `beginRecordedRun(payload.tick)`, New match — `beginRecordedRun(null)` с пустым log. Отдельной ветки инициализации рядом с Restart нет, и serialize `MatchSnapshot` с restore в core (`EOB-010`) сознательно не делается: это изменило бы границу core и требует отдельного решения.

Тик слота — такой же потолок для stepping-цикла, как тик ожидающей команды: `ceiling = min(tickCeiling, stopCeiling)`, где `stopCeiling = rebuildStopTick - snapshot.tick`. Без этого кадр, которому clamp (0.25 с = пять тиков) разрешил прошагать пять тиков, приходил бы на тик слота позже, и загруженный матч начинался бы с тика, которого в сохранении не было. Перебор тиков в accumulator при этом теряется так же, как в `0014`: точность выше ровности часов.

Валидатор проверяет форму и версии локального артефакта — и только их. Он не моделирует правила: «примет ли core эту команду» — ответ core, и она попадает в log независимо от результата. Причины отказа: `save-slot-unreadable` (не JSON или `localStorage` недоступен), `save-payload-shape`, `save-schema-version`, `save-content-version`, `save-seed-mismatch`, `save-tick-invalid`, `save-log-invalid` (нет массива или больше `MAX_SAVED_COMMANDS` записей), `save-entry-shape`, `save-entry-tick-out-of-range` (тик записи вне `[0, tick]`), `save-entry-out-of-order` (log идёт назад по тикам — replay так пересимулировать не может), `save-command-unknown`, плюс `save-slot-missing`, `save-write-failed`, `save-clear-failed` и `save-blocked-during-replay`. Каждая причина называет найденное значение, и **слот при отказе остаётся нетронутым байт в байт** — как asset contract из `0010`, потому что это тот же случай испорченного входного артефакта. `New match` — единственное действие, которое его чистит.

Явные действия вместо магии: `Save`, `Load`, `New match` и индикатор слота (`data-state` = `empty` / `ready` / `unreadable`). Слот читается на boot, после Save и перед Load, поэтому игрок всегда видит, что слот есть, до того, как что-то из него загрузится; автозагрузки нет. Save во время replay заблокирован: log под replay'ем ещё содержит команды, которых пересборка не достигла, и слот с записями past собственного тика отверг бы собственный валидатор. New match во время пересборки доступен всегда — это выход.

Измерение, как и в `EOB-017`, идёт внутри страницы: seam публикует `lastRebuild` — состояние, снятое **на тике, на котором пересборка остановилась**. Загруженный матч снова живой, поэтому чтение извне приземлилось бы на более поздний тик, и сравнивать было бы нечего. `lastRebuild` несёт `requestedTick` и `tick` (это одно и то же число, иначе свойство «тот же матч» не выполнено), полный `snapshot`, `eventCounts`, `commandCount`, `replayIndex`, `replaying`, `matchReports` и позы клипов по башням.

Предел, который knowingly не введён: у тика слота нет верхней границы, потому что content её не задаёт. Слот с правдоподобным, но огромным тиком даёт долгую пересборку вместо отказа; она видна (идёт тик и, если есть что replay'ить, badge прогресса), и `New match` в любой момент её прерывает.

### Entry screen: один оверлей в том же документе

Задача `0016` добавила вход. Ключевое решение: **вход — это слой поверх того же документа, а не вторая страница и не роутинг.** Один `index.html`, один bootstrap, один `Simulation`; отдельная страница входа означала бы второй клиент и второй набор состояний ради одного выбора.

| Решение | Что это значит в коде |
|---------|----------------------|
| Страница открывается на входе | `entryOpen = true` на boot; `openEntry(false)` ставит `game-shell[inert]` и показывает оверлей |
| Автозагрузки нет | `loadMatch` вызывается только из кнопок — дока `Load` и `Continue`; на boot слот только читается |
| Два действия | `entry-continue` и `entry-new-match`; остальные контролы входа не существуют |
| Необратимость подтверждается | первое нажатие `New match` вооружает кнопку (`data-confirm="armed"`, текст `Erase the save`), второе стирает слот |
| `MENU` ничего не стирает | `openEntry(true)` только замораживает часы; ни слот, ни log, ни core не меняются |
| Терминальный экран не тронут | `match-result`, `Restart` и `New match` в доке остались как были |

Состояния оверлея — `data-entry`: `empty` (слота нет), `slot` (слот читается), `unreadable` (слот есть, но валидатор его не берёт), `live` (вход открыт `MENU` поверх идущего матча) и `confirm` (кнопка вооружена). `confirm` описывает кнопку, а не слот, поэтому он не меняет строку слота: на вооружённом экране тик и число команд остаются теми, которые действительно лежат в слоте.

**Часы матча на входе остановлены, и это не пауза игрока.** Stepping-цикл спрашивает `!paused && !entryOpen`, поэтому «MENU ничего не меняет» — это буквально одно и то же состояние, а не приблизительное: тик, золото, снапшот и поза до и после равны сравнением. `paused` при этом остаётся ровно тем, чем игрок его оставил, поэтому Continue из `MENU` возвращает в матч, который игрок заморозил сам. Побочный выигрыш: пересборка загруженного матча идёт под оверлеем, и её можно прочитать, не гадая, что происходит на экране.

**Одно действие — один путь.** `Continue` на boot-входе вызывает тот же `loadMatch`, что и кнопка `Load` в доке, и возвращает `boolean`: отказ по слоту оставляет оверлей открытым с причиной на нём. `Continue` из `MENU` восстанавливает не слот, а идущий матч, — пересборка из слота заменила бы матч, который никто не просил заменять. seam публикует, что именно сделает Continue (`entry.continuing` = `slot` | `match` | `null`), поэтому утверждение «у входа нет своей реализации Load» проверяется, а не заявлено.

`inert` на `.game-shell` — не украшение, а запрет: пока открыт вход, клик не достаёт до pad'а и до кнопок дока. Тест проверяет это `elementFromPoint`, а не скриншотом.

Открытая оверлеем поверхность принадлежит `0013`: полная причина отказа показывается в `scene-report`, диагностика — только под `?dev`, и вход их не ломает — под флагом блок создаётся как раньше, а оверлей лежит поверх и убирается вместе с собой.

Подписи входа не сокращаются: строка слота переносится вместо `ellipsis` по тем же правилам, что и док после fix'а `0015`, и проверяется той же мерой глифов (`Range.getClientRects()` против padding box) на 1280×720 и на 560 px.

### Asset Registry

Data-слой реестра (`src/asset-registry.ts`) отвечает за fail-fast парсинг манифеста, resolve tower id → запись, кэш загрузок по файлу и `assetStatus` (`loading` / `ready` / `error`). Он не импортирует Three.js и не знает про DOM или сцену: загрузчик GLB и инстанцирование view живут в client, а путь к файлу модели получается только через `resolveModelUrl`.

Отсутствие записи для tower id — нормальный ответ, а не ошибка: такой tower остаётся процедурным. Нарушение контракта (нет манифеста, нет файла, битый GLB, нет emissive-узла, несовпадение `bytes` или `contentHash`, несовместимый тип узла, превышение бюджета) — fail-fast: viewport получает `data-assets="error"`, причина читается в `scene-status`, сцена продолжает рендериться процедурными placeholder'ами. Реестр хранит измеренные величины и факт выполнения каждой проверки, но не решает, что́ отклонять: политика в `asset-budgets.ts` и в `loadModel`, чтобы data-слой оставался без Three.js и DOM.

Владение ресурсами: загруженная сцена — единственный владелец своей геометрии, своих исходных материалов и своих клипов. Tower view получает общую геометрию и собственные копии материалов, потому что `emissiveIntensity` узла `crystal` — per-tower presentation state, и на общем материале вспышка одной башни зажигала бы все башни этого типа. `release()` view освобождает только то, чем view владеет, поэтому следующий view той же модели не получает disposed geometry.

Скелетная модель клонируется `SkeletonUtils.clone`: он пересобирает `Skeleton` и перепривязывает копию к собственным костям, а геометрию и материалы отдаёт по ссылке — поэтому копии материалов делаются после клона. `Material.copy` переносит и `envMap`, и `envMapIntensity`, и `userData`, так что per-view копия наследует владение пробой и роль `0011` без отдельного кода. Копия mixer'а и его actions снимаются в том же `release()`: mixer держит bindings и actions живыми сам по себе, и тридцать удалённых башен оставили бы тридцать mixer'ов на скелетах, которые никто не рисует.

Two-phase обновление: view, созданный до ответа реестра, остаётся процедурным; когда модель загрузилась, все существующие views этой башни заменяются на GLB на месте — entity, позиция, rotation и snapshot не меняются, поэтому момент появления модели не может сделать два replay визуально разными.

### Wails и Go

Wails — поздний desktop adapter: окно, fullscreen, settings, saves и упаковка web assets. Go не должен использоваться для высокочастотного gameplay channel. Dedicated server на Go появляется только после измерения Node.js или по решению владельца.

## 3D-ready rendering

- Первый renderer — Three.js WebGL2.
- Первая камера — OrthographicCamera.
- Мир — XZ plane с высотой по Y, даже когда визуальные объекты плоские.
- Grid — placement layer, а не система координат движения.
- Временные placeholder meshes заменяются GLB без изменения simulation contracts.
- PBR доводится IBL: `RoomEnvironment` + PMREM дают `scene.environment`. Проба — новый источник света, поэтому её вклад задаётся на материале, а не на сцене; lights, exposure и tone mapping не перенастраиваются.
- WebGPU и тяжёлые post-processing остаются последующими оптимизациями.

### Часы клипа: presentation clock, а не wall-clock

Состояние анимации живёт в presentation-слое и не попадает ни в `MatchSnapshot`, ни в `commandLog`, ни в `matchReports`: `AnimationMixer` и `action.time` — такое же presentation state, как `crystalBaseY` или `towerSlot`. Snapshot остаётся defensive projection core, а критерий детерминизма replay не меняется — «тот же seed и та же command sequence дают тот же отчёт».

Фаза клипа считается от **presentation clock**: время presentation — это `snapshot.tick * STEP_SECONDS`, то есть ровно то время, на которое матч продвинулся. Не от `elapsed` (это wall time, и он продолжает идти на паузе, как нужно ambient-bob'у), не от `performance.now()` (случайный старт дал бы визуально разный кадр на том же тике — тот самый дефект, который `0009` закрыл для моделей), не от числа кадров. Из этого следуют три свойства, и все три проверяются тестом, а не комментарием:

- **Пауза останавливает клип.** Пока `step()` не вызывается, presentation clock не растёт, разница, которую добавляет mixer, равна нулю, и поза держится: снимок на паузе и скриншот на паузе показывают одну и ту же позу.
- **Restart и replay воспроизводят позу.** Часы матча начинаются с нуля, башня появляется на своём тике (`applySnapshot` во время replay-а вызывается после шага симуляции, и `applied` view'а — это тот же тик), поэтому поза является функцией тика, а не момента, когда браузер добрался до кадра. Конечный тик матча — идеальная точка сравнения: он одинаков в обоих прогонах, и `test:core`/`matchReports` это уже доказывают.
- **Reduced-motion останавливает клип целиком.** Action не запускается (`playing: false`, `time: 0`), кости стоят в rest-позе первого ключа, который у клипа совпадает с bind-позой, поэтому читаемость позы, health bars, материалов и HUD не меняется. Включение `prefers-reduced-motion` на живом матче возвращает кости в rest-позу (`mixer.setTime(0)` до `action.stop()`) и останавливает действие.

Фаза старта клипа — слот сущности: `slot * 0.37` секунды, где slot — порядок, в котором башни построены. Две башни одной модели поэтому не стоят в одной позе, а смещение воспроизводится вместе с порядком постройки. Окно между башней и её вилкой не зависит от кадра: mixer приводится к presentation clock разницей (`applied` держит последнюю отметку), а не прибавлением дельты кадра.

Подсистема анимации — это тип `TowerClip` и три функции (`startTowerClip`, `readTowerClip`, `presentationTime`) плюс строка в `TowerView`; ни одна из них не знает про snapshot, core или DOM. Это и есть seam для будущей разбивки `src/main.ts` на `src/client/` (`EOB-014`): переносить её можно целиком, не переписывая.

### Вес environment probe — свойство материала



Сцена намеренно тёмная tactical read, поэтому проба не применяется к ней целиком. Доля пробы задаётся
`material.envMapIntensity` на каждом материале, который её видит, и объявлена одним списком
`PROBE_WEIGHTS` в `main.ts`: земля и маршруты почти не берут пробы (0.1 и 0.15 — грубая
почти-диэлектрическая поверхность не выигрывает от мягкой комнаты и только теряет свой slate),
доля растёт с metalness детали, а загруженная GLB-модель забирает пробу целиком — ради неё проба и
введена. Множителя на уровне сцены в коде нет.

Одна строка в `withProbeWeight` несущая, и её нельзя «чистить»:

```ts
material.envMap = environmentTarget.texture;
```

Three.js читает `material.envMapIntensity` **только если материал сам владеет `envMap`**. При
`envMap === null` и пробе на `scene.environment` renderer перезаписывает этот uniform значением
`scene.environmentIntensity`, и объявленный вес молча игнорируется. Это не опечатка, а правило
движка (`WebGLRenderer` при `material.envMap === null` и `MaterialProperties` для node-пути), и
проверяется только измерением: без этой строки земля на замороженном midwave-кадре светлеет примерно
на 16 единиц люминации вместо потемнения, при том что seam продолжает показывать вес как
объявленный. Поэтому seam публикует не только вес, но и `ownsProbe`, и E2E требует его у каждого
стандартного материала: отчёт не может сертифицировать значение, которого картинка не видела.

Побочный эффект, который и был целью: когда каждый стандартный материал читает пробу сам, сценовый
множитель теряет последний объект приложения и становится инертным. Возврат
`scene.environmentIntensity` в коде ничего не меняет — измерено на одинаковом кадре.

`MeshBasicMaterial` веса не несёт и не читает `envMapIntensity` вовсе: для него renderer вызывает
только `refreshUniformsCommon` и uniform не заполняет. Такие материалы (кольца pads, ауры, health
bars, burst-rings) остаются на `scene.environment` и пробу не гасят — они и не проектировались под
неё, и гасить их нечем.

## Визуальные принципы
References показывают Warcraft III/Burbenog-подачу: angled top-down camera, читаемые lanes и chokepoints, заметные build slots, плотный combat, selection outline, health bars и компактный HUD.

- Это reference для gameplay readability, а не surface design для копирования.
- Предварительный visual north-star — stylized 3D diorama с собственными models, materials, palette и HUD.
- Мир должен занимать большую часть экрана; HUD — компактный и контекстный, а не копия панели Warcraft III.
- Первые placeholder-модели должны иметь ясные silhouettes и цветовые роли, а не быть случайными grey boxes.
- Эффекты не должны закрывать маршруты, selection и состояние башен.
- Финальные models, textures и animation заменяют placeholders по asset contract, не меняя gameplay.

## LLM-friendly QA

Каждый этап должен иметь машинно-проверяемый результат:

1. Детерминированный scenario seed.
2. Фиксированные camera, viewport и tick.
3. Structured state snapshot.
4. Pure unit check.
5. Playwright E2E smoke check.
6. Screenshot для композиции и визуальных регрессий.

Для WebGL сначала проверять availability и smoke behavior, затем сравнивать screenshots с допусками. Не делать pixel-perfect проверки основным критерием gameplay correctness.

## Multiplayer compatibility

Текущий product scope — solo-first: solo остаётся режимом по умолчанию и работает без сети. Сессия с ролями, reconnect и поздним входом (`0017`, `0018`) существует и проверяется двумя browser context; PvP, раздельная экономика, accounts и matchmaking — дальше.

1. Offline session использует тот же core, что и online session.
2. Local/private rooms проверяются двумя Playwright browser contexts — выполнено в `0017`; права места, reconnect и поздний вход — в `0018`.
3. Cooperative mode определяет общие и раздельные ресурсы.
4. PvP использует отдельные match rules поверх общих primitives.
5. Client prediction добавляется только после профилирования задержки и input latency: измеренная доставка кадра на этой машине — 2–11 мс медиана по семи прогонам, но это loopback, а не сеть.
6. Accounts, matchmaking и persistence остаются внешними сервисными модулями.

## Не делать на старте

- Не создавать microservices.
- Не добавлять ECS без измеримой проблемы.
- Не выбирать WebGPU-only path.
- Не строить полноценный level editor до появления рабочего map contract.
- Не смешивать Wails IPC и realtime snapshots в один канал.
- Не хранить gameplay rules одновременно в клиенте и сервере.
